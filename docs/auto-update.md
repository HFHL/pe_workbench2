> 状态：**P0–P3/P5 初版已接（2026-10-20）：监测、通知、事件、模型写回；待真实端到端验证与来源扩展。**
>
> 只读的「盯」见 [watch.md](watch.md)：它复用这里的失效条件口径，但只汇报、不改状态/模型。

## 0. 已确认决策（2026-10-20）

| 问题 | 决定 |
|---|---|
| 原模型怎么改 | **工作副本**：`uploads/` 原文件保持只读，复制到 `exports/` 下作为可写工作模型，保留 lineage |

## 1. 任务分析

### 1.1 你想要的行为

把描述拆成五个动作：

1. **对话式建约**：框架建好后，Agent 和投资人对话，确认要盯哪些点、什么频率、什么阈值、什么情况下提醒。
2. **后台自动跑**：不需要人点“运行”，由时间（财报季、月度数据）和事件（新闻、公告、价格异动、新上传资料）驱动。
3. **自己去取证**：按监测项去查最新财务、行情、公告、新闻，而不是每次把能拿到的都抓一遍。
4. **自己判断并动手**：判断是否触发失效条件、是否需要改假设/估值/观点；有信心时直接改原模型和框架。
5. **主动通知**：需要调整模型或判断时，主动给投资人发消息，说明改了什么、为什么、依据是什么。

### 1.2 翻译成系统能力

| 能力 | 含义 | 现在有没有 |
|---|---|---|
| 监测契约 | 把“什么情况下我们错了”表变成机器可执行的对象（MON/F），带来源、频率、阈值、动作、自治级别 | 部分有（`analysis-state.json` 的 `falsifiers`），但报告表与状态没有稳定对应 |
| 对话式配置 | Agent 提方案、投资人改、确认后生效 | 没有，只有 UI 表单 |
| 调度 | 按监测项频率 + 数据日历运行 | 有全局 30s tick，但按跟踪整体跑，不按监测项 |
| 事件接入 | 新闻/公告/行情/上传 → 事件 → 匹配到监测项 | 没有 |
| 研判与变更计划 | 逐条核对 F、评估对 A/S/V/T 的影响、产出可审的计划 | 有 Skill，但没有机器可读的计划产物 |
| 分级自治 | 低风险自动改，高风险先提醒/等确认 | 没有，只有“写文件/不写文件” |
| 静默修订 | 每次更新不产生用户可见的新版本，但内部可追溯、可回滚 | 没有，每次内容变化都生成 v+1 |
| 模型写回 | 改 xlsx 输入单元格、重算、校验输出 | 没有，`workbook_query` 只读 |
| 主动通知 | 站内消息/桌面通知，带差异与操作 | 没有，只有 SSE 刷新 |

### 1.3 与现状的关键差距

- **报告是主对象**：现在每次运行都要改报告、追加 `## 跟踪记录`，于是必然产生新版本。要改成“状态是事实源，报告只在判断变化时改”。
- **模板按文件类型**：现在 `.md` 就是“投资框架复核”；要改成按“有没有监测契约”决定行为。
- **运行是整份复核**：现在一次 run 检查所有 F；要改成“到期的 F + 命中的事件”驱动，按需取数。
- **验收靠自述**：现在 Agent 说 updated 就算 updated；自动改模型前必须有宿主验收，否则不敢放开。
- **模型只读**：当前输入文件（`uploads/`）被当作只读；要自动改，必须引入“工作模型”与计算引擎。

### 1.4 关键约束

- **本机单用户、单进程**：服务不跑，监测就停。要做到“后台自动”，要么保证服务常驻（launchd），要么明确告诉用户“离线期间不监测、启动后补一次”。
- **没有 Excel 计算引擎**：当前机器没有 Excel、没有 LibreOffice，只有 openpyxl（能写公式，不能重算）。直接改 xlsx 会留下过期的缓存值。这是 P5 的硬约束。
- **输入只读是产品约定，不是硬约束**：`uploads/`、`inputs/` 现在被当作只读，但工具层只拦项目外路径；要改“原模型”，需要决定是放开输入写入，还是复制成 `exports/` 下的工作模型。
- **外部内容不可信**：新闻、网页只能当资料，不能当指令；自动决策必须能追溯到来源。

### 1.5 用你给的四个监测项做一次可行性判断

| 监测项 | 指标性质 | 适合的触发 | 主要来源 | 自动化难度 |
|---|---|---|---|---|
| MON1 DRAM ASP 季度合约价涨幅 | 行业价格，季度、结构化 | 时间（季度）+ 价格异动 | TrendForce/机构价格、westock | 中：数据可得，但口径多，需要固定口径 |
| MON2 HBM 量产节点 / 营收占比 | 公司披露 + 产业事件 | 事件（公告/新闻）+ 季度 | 公告、业绩会、行业报道 | 高：HBM 单独营收未必披露，常需代理指标 |
| MON3 月产能 kwpm / 上海厂投产 | 公司公告 + 产业事件 | 事件 + 季度 | 扩产公告、财报、调研纪要 | 高：数据零散，容易把“计划”当“投产” |
| MON4 实际毛利率 | 财务，季度、直接披露 | 时间（财报季） | 季度财报、westock | 低：最适合先自动化 |

结论：**先自动化 MON4、MON1，再逐步接入 MON2、MON3**。后两个不是“查一下就有数”的指标，应该走事件驱动 + 人工确认，不要为了自动化而编造观察值。这也决定了 P2 先做时间驱动、P3 再做事件驱动的顺序。

## 2. 目标运行流程

```text
S0 建约（对话）
   ↓
S1 触发（时间 / 事件 / 手动）
   ↓
S2 取证（适配器 → 证据）
   ↓
S3 研判（F 核对 → 影响 → 变更计划）
   ↓
S4 决策（变更等级 × 置信度 × 自治级别）
   ├─ 只观察 → 更新状态，静默
   ├─ 提醒   → 通知，不改判断
   └─ 应用   → S5
   ↓
S5 应用（状态 → 报告 → 模型 → 验收）
   ↓
S6 通知（主动消息 + 差异 + 可撤销）
   ↓
S7 审计与复盘（修订、检查点、阈值调整）
```

### S0 建立监测契约（对话）

**做什么**

1. Agent 读 `analysis-state.json`、报告第 6 节（“什么情况下我们错了”）和模型，抽出候选监测项。
2. 把候选整理成一张表：MON 编号、关联观点 T、指标、来源、频率、预警阈值、失效阈值、触发动作、阈值依据、证据。
3. 和投资人逐项确认：
   - 指标口径能不能取到数；
   - 来源是否可靠、是否要加备用来源；
   - 频率是否匹配数据发布节奏；
   - 预警/失效阈值是否沿用框架；
   - 触发后允许 Agent 做到哪一步（只提醒 / 改状态 / 改模型）。
4. 先做一次**试取数**（dry-run）：能取到的填当前值，取不到的标 `unknown` 并说明缺什么。
5. 确认后写入：
   - 状态文件：`falsifiers` 补齐 `monitor_id`、`warning`、`operator`、`next_check_at`、`autonomy`；
   - 报告第 6 节：由状态生成表格（带 MON/F ID），不再手写；
   - 调度：创建监测项与触发订阅；
   - 契约版本与确认时间。

**注意点**

- **不要自动激活**：建约必须有一次明确确认；首次先跑影子模式（只观察、不改）。
- **ID 稳定**：MON/F 一旦建立不复用；报告表格、状态、通知都用同一 ID。
- **阈值不能漂移**：Agent 只能建议，不能在建约时悄悄放宽；阈值依据必须写出来源。
- **不可观测的项不要建 watcher**：例如“HBM 良率”没有公开数据源时，标记为 `gap`，改为事件驱动（公告/调研）或人工输入，不要假装能自动查。
- **试取数失败要暴露**：数据源不可用、字段对不上、频率做不到，都应在激活前告诉用户。
- **报告表格是视图**：不要让人手改表格；改契约后重新生成，避免“报告一套、状态一套”。

### S1 触发（时间 + 事件）

**时间触发**

- 每个监测项有自己的 `next_check_at`（按 frequency + 数据日历）。
- 财报季/月度数据日可以设“数据日历”，到点检查，而不是每天盲查。
- 每日/每周摘要：把低优先级观察合并成一条。

**事件触发**

- 行情异动：单日涨跌超过阈值、价格日期更新。
- 公告/财报：新公告、业绩预告、财报发布。
- 新闻：命中主体 + 指标关键词的新文章。
- 新资料：用户上传 PDF/音频、Agent 生成新报告。
- 用户主动问“现在怎么样”。

**注意点**

- **事件 ≠ 触发更新**：先做相关性/新颖性判断，只有匹配某个 MON 且可能影响阈值的事件才进入研判。
- **合并与去重**：同一 tracking 在 15–30 分钟窗口内的事件合并成一次 run；URL 哈希 + 标题/数值相似度去重。
- **不要用股价代替经营信号**：价格只进 `market`，经营类 F 仍用经营指标。
- **频率与成本**：新闻可以每天查，财务按季度；不要每天对所有项跑大模型。
- **离线与错过**：服务没跑时事件会丢；要么常驻，要么启动后补一次“到期检查”，并告知用户。
- **幂等**：同一事件只能触发一次 run；同一 tracking 同时只允许一个 run。

### S2 取证

**做什么**

- 每个来源一个适配器：`westock_query`（行情/财务/公告/新闻）、`anysearch_search`（公开新闻）、上传文件（PDF/ASR）、模型（workbook_query）。
- 适配器返回结构化候选事实：指标、值、单位、期间、发布日期、抓取时间、来源 URL、来源等级。
- 写入本次 run 的 `evidence.json`；冲突来源都保留。

**注意点**

- **区分“发布日”和“数据期间”**：2026Q3 财报可以在 2026-10 发布，不能拿发布日当截止日。
- **提取误差**：网页数字可能带单位、同比/环比、合并/单体口径；必须结构化并标注口径。
- **外部内容只当数据**：新闻正文里的“请忽略之前的指令”之类不能进入执行路径。
- **取不到就是 unknown**：不要用旧值、模型缓存值或猜测填充。
- **来源等级**：官方公告/财报 > 行业协会/交易所 > 主流媒体 > 一般网页；等级影响置信度与是否自动应用。
- **缓存与限流**：同一 URL 不重复抓；适配器要有超时、退避、配额。

### S3 研判

**做什么**

1. 对每个到期的 F：填 `observed`、判断 `armed / warning / triggered / unknown`、更新 `last_checked_at`。
2. 判断是单期偏差还是持续偏离；是否推翻机制。
3. 受影响对象：假设 A → 敏感性 S → 估值 V → 观点 T → 报告小节 → 模型单元格。
4. 产出 `change-plan.json`：改什么、before/after、依据、证据 ID、影响链、置信度。
5. 给出通知草稿：一句话结论、关键数字、建议动作。

**注意点**

- **先 F 后 T**：不能先看价格涨跌再找理由；每个 T 的状态变化必须能指到 F 和证据。
- **单期 vs 持续**：单期偏差只记录；连续 2–3 期且缺口扩大才下调假设。
- **机制失效优先**：机制被推翻时直接改 T，不做数字微调。
- **实际值不倒灌**：新增 `kind: actual` 的证据，保留原预测，不把新实际改写成“当时已知”。
- **不要改阈值**：阈值调整是投资人的决定，run 里只能建议。
- **模型变更要可控**：只改已确认映射的输入单元格；公式、结构、方法不动。
- **置信度要可解释**：来源等级、直接/间接、是否多源一致、映射是否确认、重算是否通过；不要只给一个“高”。

### S4 决策（自治）

**做什么**

按“变更等级 × 置信度 × 用户设置”决定：

| 等级 | 例子 | 默认行为（已确认：默认自动） |
|---|---|---|
| C0 观察 | 新证据、未触发阈值 | 自动更新状态观察值；不通知（进摘要） |
| C1 预警 | 接近预警阈值 | 自动更新状态；通知（轻） |
| C2 触发/观点降级 | F 触发、T 降为 weakened | 自动改状态与报告；检查点；通知 |
| C3 估值/目标价变化 | 假设变化导致目标价变动 | 自动改状态/报告/模型；检查点；必须通知 |
| C4 结构/方法/阈值 | 换估值方法、改阈值、改观点框架 | 生成计划 + 通知，等确认 |

**注意点**

- **自动不等于无门槛**：C2/C3 自动应用仍要求高置信度（见 3.3）；低置信、来源冲突、映射未确认时降级为提议。
- **C4 保留人工确认**：改阈值、换方法、删观点、改历史实际值属于投资人的判断，不自动。
- **高风险必须提醒**：只要改了模型或目标价，即使自动应用，也要通知并给撤销入口。
- **可撤销**：每个自动变更都要有对应的修订 ID 和撤销动作。
- **信任提升**：虽然默认自动，建议第一周先看通知与差异，必要时把某个 MON 降为“仅提议”。

### S5 应用

**做什么**

1. 按顺序写：状态文件 → 报告受影响小节 → 模型输入单元格 → 重算 → 校验。
2. 写前备份/快照；写临时文件后原子替换；同一目标加锁。
3. 校验：状态结构、ID 对应、版本/截止日、报告与状态一致、模型输出在合理范围。
4. 记录 `change-set`（对象、before/after、证据、run ID）。

**注意点**

- **没变化就不写报告**：C0 只改状态观察值；报告不动，自然没有新版本。
- **报告只在判断变化时改**：不要把“本期检查”写进报告；检查记录放数据库/时间线。
- **模型写入要原子**：先复制、再改、再重算、再校验、最后替换；失败不能留下半成品。
- **公式与格式**：openpyxl 可能丢图表/样式；xlsm 还要保留 VBA。写回前必须用真实模型做回归。
- **重算**：没有计算引擎就不要写 xlsx；否则缓存值是旧的，等于假更新。
- **验收失败不能显示成功**：状态只能是 `needs_review` / `failed`。

### S6 通知

**做什么**

- 站内通知中心（必选）；可选 macOS 桌面通知；后续可接邮件/IM。
- 一条通知包含：级别、结论、关键数字、改了什么、依据来源、置信度、已执行/待确认、撤销/查看/调整。
- 用户可直接回复“把阈值改成 15 周”“以后这类先问我”，Agent 更新契约。

**注意点**

- **只通知有决策价值的事**：无变化进日报；重复新闻不通知；预警不要天天响。
- **分级**：FYI / 需要知道 / 需要行动。
- **限流与静默时段**：每 tracking 每天最多 N 条，合并同类；夜间可静默。
- **可解释**：必须能点开证据和差异；不要只说“我觉得要调整”。
- **不打断当前对话**：通知进收件箱/监测动态，不直接插入用户正在聊的会话。
- **失败也要通知**：连续取不到数、模型写入失败、验收失败，都属于需要知道的事。

### S7 审计、检查点与复盘

**做什么**

- 每次应用生成内部修订；按策略生成用户可见检查点。
- 记录监测项状态变化、通知、用户操作（确认/撤销/改阈值）。
- 每周/每月复盘：哪些提醒有用、哪些是噪声、哪些项长期取不到数。

**注意点**

- **“不生成新版本”不等于“没有审计”**：内部修订保留，UI 默认只看检查点。
- **检查点触发**：C2 以上、目标价变化超阈值、手动、周/月摘要；C0/C1 不产生可见版本。
- **保留策略**：内部修订可压缩/定期清理，但检查点与变更集长期保留。
- **复盘只建议不改阈值**：阈值调整仍要用户确认。

## 3. 核心机制

### 3.1 监测项 schema

把截图里的表变成对象（示例）：

```json
{
  "id": "MON1",
  "falsifier_id": "F1",
  "thesis_id": "T1",
  "metric": "DRAM blended ASP 季度合约价涨幅",
  "operator": "crosses_below",
  "warning": "2026Q3/Q4 涨幅收窄至 20% 以下",
  "threshold": "2027 年前价格明显回落，毛利率跌至 60% 以下",
  "unit": "%",
  "source": {
    "kind": "industry_price",
    "primary": "westock_query",
    "query": "DRAM 合约价 季度 环比",
    "fallback": "anysearch_search",
    "tier": 2
  },
  "frequency": "quarterly",
  "action": "下调营收/毛利率假设，重估目标价",
  "rationale": "模型假设 2026E ASP 约 $1.095/Gb、毛利率 84%；纪要预测 2026Q3/Q4 涨幅 20–30%",
  "evidence_ids": ["E12", "E13"],
  "status": "armed",
  "last_observed": "+4% QoQ",
  "last_checked_at": "2026-10-18",
  "next_check_at": "2026-11-15",
  "autonomy": "auto_notify",
  "notify": "on_warning"
}
```

状态扩展：`armed / warning / triggered / unknown / retired`。现在的 schema 只有 `armed / triggered / unknown / retired`，需要补 `warning`，否则截图里的“预警阈值”没有落点。

### 3.2 触发模型

```text
时间：每个 MON 的 next_check_at + 数据日历
事件：行情异动 / 公告 / 新闻 / 上传 / 用户提问
        ↓ 去重、相关性、匹配 MON
        ↓ 15–30 分钟合并窗口
一次 run：只检查“到期 + 命中”的 MON
```

- 不为每个 MON 单独起一次 Agent；按 tracking 聚合。
- 事件先经过规则/轻量模型分诊，再决定是否进入主 run。
- 价格类事件只更新 `market`，不触发经营 F。

### 3.3 证据与置信度

置信度由宿主计算，Agent 只提供理由：

| 信号 | 高 | 中 | 低 |
|---|---|---|---|
| 来源 | 公告/财报/交易所 | 行业协会/主流媒体 | 一般网页/传闻 |
| 口径 | 指标直接披露 | 可由多项推算 | 间接/代理 |
| 一致性 | ≥2 个独立来源一致 | 单一可靠来源 | 来源冲突 |
| 时效 | 在频率窗口内 | 略过期 | 过期/期间不明 |
| 映射 | 已确认 | 待确认 | 未映射 |

- 自动应用要求：来源高/中 + 口径直接/可推算 + 映射已确认；涉及模型时还要求重算通过。
- 来源冲突、口径不一致、映射未确认 → 只能提议。

### 3.4 自治与版本

| 等级 | 行为 | 通知 | 版本 |
|---|---|---|---|
| L0 观察 | 只记录观察值 | 否（摘要） | 内部修订 |
| L1 提醒 | 记录 + 通知 | 是 | 内部修订 |
| L2 自动改状态/报告 | 应用 + 通知 | 是 | 内部修订；C2 生成检查点 |
| L3 自动改模型/目标价 | 应用 + 通知 + 撤销入口 | 是（必须） | 写前安全检查点 |
| L4 仅提议 | 生成计划，等确认 | 是 | 无文件变更 |

默认：新建约 L0/L1；C3/C4 固定 L4；用户可按 MON 或按等级提升。

### 3.5 静默修订与检查点

这是“不要每次生成新版本”的落地方式：

- 每次写入仍保存内容（blob）与差异，但标记为 **internal revision**，不出现在版本选择器。
- **checkpoint** 只在以下情况生成：
  - 观点状态变化（C2+）；
  - 目标价/估值变化超过阈值；
  - 手动“保存检查点”；
  - 周/月摘要；
  - 模型写入前（安全快照）。
- UI 默认展示“检查点 + 变更时间线”，点开可看每次内部修订的 diff。
- 报告不再每次追加 `## 跟踪记录`；检查记录进数据库。若希望报告里保留痕迹，只在生成检查点时追加一行摘要。

### 3.6 模型写回

先明确“模型”指哪一层：

| 层 | 内容 | 可写性 |
|---|---|---|
| L1 状态 | `analysis-state.json`（假设、估值、观点） | 始终可写 |
| L2 报告 | 投资框架 Markdown | 始终可写 |
| L3 工作簿 | 源 xlsx | 需要工作副本 + 计算引擎 |

**工作副本（已确认）**：建立监测契约时，把 `uploads/` 的原模型复制为 `exports/<subject>/model/工作模型.xlsx`，原上传保持只读；之后自动更新只改工作副本。这样既不破坏“输入只读”，又能持续更新，并保留 `model_file` 指向原始文件、`working_model` 指向工作副本。

**写回链路**：

```text
确定映射（指标/假设 → sheet!cell）并人工确认
  → 复制工作簿到临时文件
  → openpyxl 写输入单元格
  → 计算引擎重算（LibreOffice headless / Excel AppleScript / formulas）
  → 读关键输出（目标价、收入、毛利率）
  → 与预期方向/幅度比对
  → 通过后原子替换
```

**计算引擎（已确认：LibreOffice）**：

| 方案 | 状态 | 说明 |
|---|---|---|
| LibreOffice headless | **采用**，安装到 `~/Applications` | 用 `soffice --headless` 重算；服务端通过 `SOFFICE_BIN` 定位 |
| Excel + AppleScript | 备选 | 依赖本机装 Office；当前未安装 |
| Python `formulas` | 兜底 | 复杂模型函数覆盖不全，只用于验证 |
| 不写 xlsx，只维护状态模型 | 降级路径 | 计算引擎不可用时使用 |

**结论**：先安装并验证 LibreOffice 能对真实模型完成“写单元格 → 重算 → 读输出”的闭环；验证通过后，P5 才允许自动改工作模型。没有重算结果时，仍然只出变更计划。

### 3.7 通知模型

```json
{
  "id": "ntf-...",
  "tracking_id": "trk-...",
  "run_id": "run-...",
  "severity": "info | attention | action",
  "title": "MON2 触发：HBM 营收占比仍为个位数",
  "body": "…",
  "changes": ["T2: active → weakened", "目标价 100 → 92"],
  "actions": ["查看差异", "撤销", "调整阈值", "以后先问我"],
  "created_at": "...",
  "read_at": null
}
```

- 站内通知中心 + 监测动态；桌面通知用 macOS `osascript -e 'display notification ...'`（零依赖、成本最低）。
- 通知不是聊天消息，但可以“回复”转成一次对话（跟踪助手）。
- 同类合并、限流、静默时段；无变化只进摘要。

### 3.8 报告、状态、日志的职责

| 对象 | 角色 | 更新时机 |
|---|---|---|
| `analysis-state.json` | 事实源：F/T/A/S/V、观察值、检查游标 | 每次 run（观察值）；判断变化时改状态 |
| 报告 | 人的视图：结论、观点、敏感性、失效条件 | 只在判断/结论变化时改；表格由状态生成 |
| 数据库 | 运行、事件、证据、变更、通知、修订 | 每次 run |
| 内部修订 | 审计与回滚 | 每次写入 |
| 检查点 | 用户可见版本 | C2+ / 手动 / 周期 |

这样既满足“每次更新不产生新版本”，又不丢审计。

### 3.9 单一契约

上一轮分析发现的根因是契约分散。新流程必须共用一份 `monitoring contract`：

- 监测项字段、状态机、自治等级；
- 触发规则、置信度规则、变更等级；
- prompt 片段、结果 schema；
- UI 文案与测试 fixture。

建议落到 `lib/monitoring-spec.mjs`（或 `skills/monitoring/contract.md` + 代码常量），server、UI、测试都引用同一份，避免再出现三套 schema。

### 3.10 来源分级与高频站点

事件驱动最容易死在“来源不可靠 + 抓得太勤”。来源必须分级，并绑定抓取策略：

| 等级 | 来源 | 用途 | 策略 |
|---|---|---|---|
| S1 | 交易所公告、公司财报/IR、监管文件 | 可作为触发/自动应用的依据 | 优先抓；保留原始 URL 与抓取时间 |
| S2 | 行业协会/价格机构（TrendForce 等）、主流财经媒体 | 可作为观察与预警依据 | 需要交叉验证；标注口径 |
| S3 | 高频资讯站（如 `stock.cfi.cn`）、聚合页、一般网页 | 只作为线索，不能单独触发自动改模型 | 低频轮询、缓存、去重；必须回到 S1/S2 核实 |
| S4 | 论坛、社交媒体、传闻 | 只进“待核实”，不触发 | 默认不抓或只做提示 |

**高频站点（cfi.cn 这类）的注意点**：

- **只当线索**：页面更新快、重复多、口径不统一，不能因为一条标题就改模型；必须回到公告/财报或第二个独立来源。
- **限流与缓存**：每个域名设最小抓取间隔（如 5–15 分钟）、条件请求（ETag/Last-Modified）、内容哈希去重；不要按监测项逐个抓同一个页面。
- **抓取范围**：只抓与主体/指标相关的栏目或详情页，不整站爬；遵守 robots/服务条款，失败退避。
- **解析稳定**：页面结构会变；适配器要有字段校验和“解析失败”告警，不能把空值当 0。
- **来源标注**：通知与结果里必须显示原始 URL、标题、发布时间、抓取时间；用户能点开核对。
- **可信度降级**：S3 来源即使命中，也只生成“待核实”通知；自动应用需要 S1/S2 佐证。
- **反注入**：网页内容只做事实抽取，不执行页面里的任何指令；URL 进白名单/黑名单校验。

实现上，`source_events` 记录 `source_tier`、`domain`、`content_hash`、`fetched_at`、`published_at`、`triage_status`；`monitor_items.source` 绑定主来源和兜底来源。这样同一份 evidence 既能让 Agent 判断，也能让宿主按等级决定是否允许自动应用。

## 5. 开发流程

> 原则：先让“监测—研判—通知”闭环跑通，再放开写模型；每一步都能单独验收、单独回退。

### P0 契约与可行性（先设计，不写业务）

**交付**

- 监测契约 schema（MON/F、warning 状态、autonomy、next_check）。
- 变更等级 / 置信度 / 通知策略的规则表。
- 版本策略：internal revision vs checkpoint。
- 两个技术验证：
  1. 用真实模型验证 openpyxl 写入 + 计算引擎（LibreOffice/Excel/formulas）的可行性；
  2. 用真实报告验证第 6 节表格 → F/MON 的提取与 ID 对齐。

**注意点**

- 先定“状态是事实源”，否则后面又会回到改报告。
- 不要先写 UI 再定契约。
- 技术验证要设时间盒；xlsx 不可行就明确降级为“计划 + 提醒”。

**验收**：schema 文档、规则表、验证报告（含失败结论）。

### P1 对话式建约 + 试取数

**交付**

- 新 Skill（如 `monitor-setup`）：读框架 → 提监测方案 → 对话修改 → 写状态/报告/调度。
- UI：方案预览、逐项编辑、试取数结果、确认激活。
- 试取数：对每个 MON 跑一次适配器，能取到的填值，取不到的标 unknown。
- 影子模式开关：只观察，不写文件。

**注意点**

- 必须有人工确认；不能“建完框架就自动开始监控”。
- 没有状态文件的旧报告先补建，不要直接建监控。
- 不可观测项不要建 watcher；标 gap 或事件型。
- 方案要能导出/审阅，避免黑箱。
- 确认后写契约版本和时间，便于以后解释行为变化。

**验收**：从一个真实框架生成 4 个 MON；试取数能区分“有数/无数”；确认前不产生后台运行。

### P2 时间驱动闭环（不写模型）

**交付**

- 按 MON 到期检查；按 tracking 聚合；一次 run 只查到期项。
- Agent 产出观察值 + 变更计划；宿主应用状态；报告仅在判断变化时改。
- 内部修订 + 检查点；无变化不产生可见版本。
- 通知中心 MVP（站内）。
- 超时、失败、unknown、错过检查的处理。

**注意点**

- 报告不再每次追加跟踪记录；否则版本问题没解决。
- 状态每次写是正常的，但要标 internal。
- 取不到数要显式 unknown，不能静默跳过。
- 价格只更新 market。
- 本机休眠/服务停止要提示，不要假装一直在监控。
- 先影子模式跑一段时间，校对 Agent 的观察值。

**验收**：连续 10 次无变化检查不产生可见版本；1 次触发产生 1 条通知 + 1 个检查点；unknown 有记录。

### P3 事件驱动

**交付**

- 事件表 + 适配器（westock 公告/新闻、anysearch、上传文件、行情异动）。
- 分诊：主体/指标匹配、新颖性、来源等级；事件 → MON 映射。
- 合并窗口、去重、限流。
- 事件触发 run 与时间触发共用同一研判/应用链路。

**注意点**

- 先规则后模型；不要让每条新闻都跑主模型。
- 事件相关性判断要可解释（命中了哪个 MON、哪个关键词）。
- 外部内容防注入；只抽事实。
- 回放测试：用固定事件集验证不会重复触发/漏触发。
- 噪音率是核心指标；宁可少报，不要天天误报。

**验收**：回放 50 条事件，重复触发 0，无关事件不触发主 run；命中事件能定位到 MON。

### P4 分级自治 + 主动通知

**交付**

- 变更等级 × 置信度 × 自治级别矩阵。
- C2 自动应用（状态/报告），C3 默认提议，C4 永远提议。
- 通知内容模板、操作（查看/撤销/调整/以后先问）。
- 信任提升流程：影子 → 逐项放开。
- 撤销与检查点。

**注意点**

- 默认保守；先让用户看到“它想改什么”，再放开。
- 置信度由宿主算，不能只看 Agent 自评。
- 每个自动变更必须可撤销。
- 通知疲劳：合并、限流、静默时段。
- 自动改目标价/观点失效必须有醒目提示。

**验收**：高置信触发自动改 + 通知 + 可撤销；低置信只提议；误报率可统计。

### P5 模型写回

**交付**

- 工作模型副本与 lineage。
- 指标/假设 → 单元格映射（人工确认）。
- openpyxl 写入 + 计算引擎重算 + 输出校验。
- 写前快照、原子替换、失败回滚。
- 模型变更进入通知与变更集。

**注意点**

- 没有重算引擎不写 xlsx。
- 先在工作副本上做，原上传不动。
- 用真实模型回归：图表、样式、命名区域、公式、xlsm 宏。
- 只改已确认的输入单元格；公式/结构/方法变更需人工。
- 输出偏差超预期时拒绝写入并通知。
- 自动改模型前先跑一段“只出计划”的影子模式。

**验收**：真实模型改一个假设 → 重算 → 目标价变化符合预期；失败可回滚；公式未被破坏。

### P6 硬化与迁移

**交付**

- 预算/限流/重试/看门狗/并发控制。
- 指标与日志：检查次数、run 成功率、误报率、通知打开率、成本。
- 旧 tracking/报告迁移；文档与演示数据修复。
- 复盘界面：哪些 MON 长期 unknown、哪些阈值从没触发。

**注意点**

- 成本要可见；按 tracking/天设上限。
- 失败要能定位到“取数/研判/写入/通知”哪一段。
- 迁移不能丢旧运行记录。
- 文档只保留一份契约，其他引用。

## 6. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 本机休眠/服务停止 | 监测停摆，用户以为在跑 | 明确在线状态；launchd 常驻；启动补检 |
| 数据源不稳/口径不一 | 误判触发 | 多源、来源等级、unknown、人工确认 |
| 新闻误报/重复 | 通知疲劳，信任下降 | 分诊、去重、合并、限流、影子模式 |
| 自动改模型出错 | 投资结论被污染 | 映射确认、重算、校验、快照、回滚 |
| xlsx 写入破坏格式/公式 | 模型不可用 | 工作副本、真实模型回归、失败回滚 |
| Prompt injection | Agent 执行网页指令 | 外部内容只作数据、结构化抽取、工具白名单 |
| 成本失控 | 账单/延迟 | 分诊、预算、频率、缓存 |
| “无版本”导致无法追责 | 审计缺失 | internal revision + change set + checkpoint |
| 用户不知道 Agent 改了什么 | 信任问题 | 主动通知、差异、检查点、撤销 |

## 7. MVP 建议与待确认

### 7.1 建议的 MVP

**第一版先做“时间驱动 + 状态/报告自动更新 + 站内/桌面通知 + 静默修订 + 工作模型”**：

- 对话式建约；
- 按 MON 到期检查；
- C0–C3 默认自动应用（受置信度约束），C4 仍确认；

- 触发时通知，并给撤销入口；
- 模型写回在 LibreOffice 验证通过后启用；未通过时只出变更计划。

第二版加事件驱动；第三版加高频来源与更细的自治策略。这样每一版都能独立验证，不会一开始就赌“Agent 能安全改 Excel”。

### 7.2 已确认与保留边界

已确认（2026-10-20）：

1. 原模型走 **工作副本**，`uploads/` 不直接改。
2. 安装 **LibreOffice**，headless 重算。
3. **默认自动改**（C0–C3），C4 保留确认。
4. **站内通知**必选，桌面通知用 macOS `osascript`；邮件/IM 以后。
5. 事件源覆盖 westock + anysearch + 上传文件；高频站点（如 `stock.cfi.cn`）按 S3 线索处理，必须回到 S1/S2 核实。

仍然保留的硬边界：

- C4（改阈值、换方法、删观点、改历史实际值）不自动。
- S3 来源不能单独触发自动改模型。
- 低置信、来源冲突、映射未确认 → 只能提议。
- 所有自动变更必须有内部修订、检查点或撤销入口。
- 不自动交易。
